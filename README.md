# Restaurant-Incremental-ETL-Pipeline-Python-PostgreSQL
Python + PostgreSQL incremental ETL pipeline for loading restaurant data from CSV into a staging table using created/modified timestamps, UPSERT logic, and ETL execution logging.
# Restaurant Incremental ETL Pipeline

A Python and PostgreSQL ETL pipeline that incrementally loads
restaurant data from a CSV source into a PostgreSQL staging table.

The pipeline uses the source `created` and `modified` timestamps
to identify newly created or modified records. Only those records
are loaded into the staging table.

The project also maintains an ETL log table that records when the
staging ETL job was executed.

---

## Architecture

                    restaurants.csv
                           |
                           v
                     Python / Pandas
                           |
                           v
                    Read source data
                           |
                           v
                 Get last ETL ingestion time
                           |
                           v
              Filter new / modified records
                           |
                           v
                   restaurants_stag
                           |
                           v
                       UPSERT
                           |
                           v
                        etl_log

---

## Problem Statement

A full load processes every restaurant record every time the ETL
runs.

Example:

    Run 1 -> 100,000 rows
    Run 2 -> 100,000 rows
    Run 3 -> 100,000 rows

This is inefficient when only a small number of records change.

The incremental pipeline processes only newly created or modified
records.

Example:

    Run 1 -> 100,000 rows
    Run 2 -> 250 rows
    Run 3 -> 80 rows

## Source Data

The source CSV contains:

    restaurant_id
    restaurant_url
    restaurant_name
    address
    location
    phone
    rating
    created
    modified

The `created` and `modified` columns are used for incremental
change detection.

---

## Staging Table

The staging table contains:

    restaurant_id
    restaurant_url
    restaurant_name
    address
    location
    phone
    rating

The following fields are intentionally NOT stored in staging:

    created
    modified
    ingestion_date
    start_time
    end_time

`created` and `modified` are used only to determine which records
should be loaded.

`ingestion_date` belongs to the ETL logging layer.

---

## ETL Log Table

The ETL log table contains:

    log_id
    script_name
    ingestion_date

Example:

    log_id | script_name              | ingestion_date
    -------|--------------------------|---------------------
    1      | restaurant_staging_load  | 2026-08-25 21:30:10
    2      | restaurant_staging_load  | 2026-08-26 21:31:02

The ingestion timestamp is automatically generated by PostgreSQL
using:

    DEFAULT CURRENT_TIMESTAMP

---

## Incremental Loading Logic

The pipeline first retrieves the most recent ETL execution time:

    SELECT MAX(ingestion_date)
    FROM etl_log
    WHERE script_name = 'restaurant_staging_load';

If there is no previous run, the pipeline starts from:

    1900-01-01 00:00:00

The source data is then filtered using:

    created > last_ingestion_date
    OR
    modified > last_ingestion_date

Therefore:

    New record
        -> created after previous run
        -> LOAD

    Modified record
        -> modified after previous run
        -> LOAD

    Old unchanged record
        -> SKIP

---

## UPSERT / SCD Type 1 Behavior

The staging table uses:

    ON CONFLICT (restaurant_id)
    DO UPDATE

Therefore:

    New restaurant_id
        -> INSERT

    Existing restaurant_id
        -> UPDATE

Example:

Before:

    restaurant_id | restaurant_name | rating
    --------------|-----------------|-------
    100           | Jalsa           | 4.1

New source record:

    restaurant_id | restaurant_name | rating
    --------------|-----------------|-------
    100           | Jalsa           | 4.5

After ETL:

    restaurant_id | restaurant_name | rating
    --------------|-----------------|-------
    100           | Jalsa           | 4.5

This behaves similarly to SCD Type 1 because the old value is
overwritten rather than historically preserved.

---

## Transaction Handling

The staging load and ETL logging are executed in one transaction.

Successful run:

    Load staging
         |
    Write ETL log
         |
       COMMIT

Failed run:

    Error
      |
    ROLLBACK

This prevents partial changes from being committed.

## Installation

Clone the repository:

    git clone <YOUR_GITHUB_REPOSITORY_URL>
    cd restaurant-incremental-etl

Create a virtual environment:

    python -m venv venv

Activate on Windows:

    venv\Scripts\activate

Install dependencies:

    pip install -r requirements.txt

---

## Environment Variables

Create a `.env` file in the root directory:

    DB_HOST=localhost
    DB_PORT=5432
    DB_NAME=restaurant_db
    DB_USER=postgres
    DB_PASSWORD=your_password

Never commit `.env` to GitHub.
